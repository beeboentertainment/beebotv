H.264, H.265 and AV1: what Beebo actually does.

Beebo has H.264 live transcoding and a built AV1 encoding engine. H.265/HEVC originals can also play on compatible devices or be repackaged without re-encoding the video. The missing live output choice is HEVC encoding, not every form of HEVC support—and not the AV1 encoder.

AV1 output passed small local software-encoding checks. A separate automatic-selection issue can choose H.264 when AV1 was requested and still needs correction; AV1 is not presented as fully ready for all players.

Playing an existing file, decoding it for conversion and encoding a new video stream are different capabilities. No single codec is the best choice for every device or connection.

What the missing HEVC output option means for you.

Your existing HEVC movie can still play.

If your device can play the original file and your connection can carry its bitrate, there is no reason to create another HEVC stream. Original playback or a compatible remux can retain its video bitstream.

A different output can help an older player.

If the source cannot play directly, Beebo can decode a supported input and create H.264 output. Optional AV1 encoding is built, with an automatic-selection correction still needed. A working decoder, encoder and enough computer capacity are required.

It matters for some lower-bandwidth setups.

A device that supports HEVC but not AV1 could benefit from an HEVC re-encode at a lower bitrate. That output choice is missing. H.264 may need more data for comparable detail, or you may choose a smaller output size.

Why is HEVC live output not offered yet? The reviewed implementation connects its live conversion ladder to H.264 and AV1, not HEVC. Completing HEVC output would require encoder selection, stream packaging, device negotiation, fallback and playback testing. Seeing an HEVC encoder in a media library or GPU capability list is not enough. No release date is announced here.

For a compatible original file, this missing output choice may make no difference. For a constrained connection or a specific receiving device, it can matter. Beebo’s other routes are useful alternatives, not proof that every workload is covered.

Does a missing output codec remove 4K or HDR playback?

No. Original playback and repackaging can retain supported source resolution and HDR signalling. Those routes still need the right decoder, display and bandwidth. But Beebo’s reviewed new live output ladder stops at 1080p and targets 8-bit SDR; correct HDR-to-SDR tone mapping requires a working, tested path. A 4K original, a 4K-to-1080p conversion and a new 4K HDR encode are three different capabilities.

Remuxing does not lower video bitrate. If bandwidth is the problem, merely changing MKV to MP4 will not solve it. Where tone mapping is needed, the host also needs a working tone-map path; source detection alone does not confirm correct colours.

What do Baseline, Main, High, Main 10 and level numbers mean?
Codec
The compression language: for example H.264/AVC, H.265/HEVC or AV1.
Profile
A set of coding tools and constraints inside that codec. H.264 Baseline, Main and High are different profiles. HEVC Main and Main 10 distinguish, among other limits, support for 8-bit versus up to 10-bit samples. A higher-sounding profile is not automatically the right output for an older player.
Level
A limit on decoder workload, such as picture size, picture processing rate and bitrate. It is not a picture-quality score or an app release number.
Bit depth / HDR
Bit depth describes available sample precision. Ten-bit video is not automatically HDR, and a codec name alone does not identify the colour transfer, metadata or display capability.
Container / delivery
MP4 and MKV package streams. HLS delivers playlists and segments. These are not video codecs.

Format profiles and levels are described in the H.264, H.265 and AV1 specifications; HDR signal characteristics are separately defined in BT.2100.

Beebo’s encoder settings: the inspected hardware H.264 paths request High profile. OpenH264 does not receive one explicit profile/level setting here, so its actual output must be inspected. The optional libx264 path explicitly requests High, level 4.1; that encoder is not included in the inspected Windows media bundle. AV1 NVENC requests Main profile. These are conditional encoder arguments, not a claim of every possible profile or level.

It would be misleading to advertise “all H.264 versions.” Actual support depends on the source profile, the selected encoder/decoder, frame rate, resolution, driver and player.

Is AV1 the highest codec, or is that H.266?

There is no single “highest” codec. AV1 is a separate specification; H.266, also called VVC, is another video coding standard. Read the H.266 definition. Newer compression tools can improve efficiency, but deployment, encoding cost and device compatibility affect whether they are useful. This review does not establish a supported Beebo VVC playback or output workflow, so none is advertised.

The relevant question is whether your source, host and viewing device support the same practical route—not which codec has the largest number.

JIT is real transcoding. It still has a workload.

Beebo can decode, resize, process and re-encode video on demand; it is not limited to changing containers or asking the phone to do all the work. “Just in time” describes when the processing happens. It does not remove the cost of decoding, filtering and encoding each required frame. How the media processing pipeline works.

Equal bitrate is not automatic data saving. At the configured 1080p targets, 8 Mbps video plus 192 Kbps stereo audio is about 3.69 GB per hour, using decimal GB, before overhead or bitrate variation. The same target is used for H.264 and AV1. A more efficient codec can improve the quality achievable at a chosen bitrate, but Beebo does not currently promise a fixed percentage saving by changing codec.

The common rate-control arguments request a maximum video rate of 1.5× the target and a buffer size of 2× the target. The SVT-AV1 route instead supplies a target bitrate without those maximum/buffer arguments. These encoder controls are not network traffic caps or guarantees of identical output size.

Three ways to reach the same player

01 · ORIGINAL

Direct Play

A compatible device receives the original file. The video is not re-encoded. Byte-range requests let the player fetch the needed portion and seek without first downloading the whole movie.

02 · REPACKAGE

Direct Stream / remux

When the picture works but the container does not, compatible video can be copied into a streaming container. Audio may be copied or converted independently. Repackaging the picture preserves its encoded bitstream.

03 · CONVERT

On-demand transcoding

The computer encodes a compatible stream when the player, selected quality or subtitle choice requires it. This uses processing power and can change picture or sound quality. The library original stays unchanged.

JIT means just in time. Beebo generates conversion pieces near the position being watched. It does not have to convert the whole movie before playback. This is a practical resource-management design, not proof that Beebo is always faster than another product.

How the on-demand engine manages work

Segments, seeking and temporary storage
  • H.264 conversion uses HLS with 4-second MPEG-TS segments. Optional AV1 uses fragmented MP4 segments and an initialization segment.
  • The playlist represents the full video timeline. A seek far from current work restarts preparation near the requested time.
  • Default conversion pacing stops work when more than 45 segments ahead, resumes within 15, and retains 6 behind: roughly 180 seconds ahead and 24 seconds behind at 4 seconds per segment.
  • An idle conversion session is removed after about 3 minutes by default. These are session defaults, not a fixed disk-byte allowance or a guarantee that a whole movie is cached.
  • Remuxing uses a different path: approximately 6-second pieces aligned to source keyframes. A first keyframe scan may delay start; preparation can be retried instead of promising an instant first frame.
CPU, GPU, queueing and recovery
  • Beebo performs a short test encode to discover working encoders, rather than assuming an encoder listed by FFmpeg means a working graphics card is present.
  • H.264 candidates include NVENC, QSV, AMF, VideoToolbox and platform-specific VAAPI, with software fallback where available. The inspected Windows bundle includes OpenH264; it does not include libx264 or libx265.
  • Protective conversion defaults are 1 job on a low-capacity profile, 2 on a normal profile, or 3 on a high-capacity profile, with one additional slot when hardware encoding is active. Owner overrides and actual workload matter.
  • Busy conversion requests use a retry queue. Encoder failures can move the session to another supported encoder or processing method. If every route fails, playback may still fail.
  • The base stalled-encoder wait is 10 seconds while a viewer is waiting, adjusted for large input dimensions and low-capacity profiles. It is not a promised startup time.
Optional AV1 and preparation ahead of watching

AV1 output is implemented as an additional opt-in path. Normal negotiation requires owner permission and a player that declares AV1 decoding. It is disabled by default. Compatible hardware or a working software encoder is required, and H.264 is the fallback if no AV1 encoder is usable.

Playing an existing AV1 original is a separate capability from making a new AV1 stream. Current converted output is SDR; a newer codec does not guarantee lossless quality or preserved HDR.

The owner can select an item for background stream preparation. This is a session-cache pilot, not a permanent optimized library or an automatic whole-library overnight scheduler.

Why the exact version is useful

Version numbers help testers reproduce behavior, identify compatibility changes and compare like-for-like builds. They do not establish that one app is faster, safer or higher quality. Decoder support, encoder settings, operating system, driver, display, receiver and network must be recorded too.

Open-source technology names identify components used by Beebo, not endorsements or competitor rankings. The notices distributed with the application remain applicable.

A useful playback test report
  1. Record the app version, distribution, computer, operating system and playback device.
  2. Use an original or authorized sample and record container, video codec, dimensions, audio and subtitles.
  3. Record the selected quality and actual path: Direct Play, remux or conversion.
  4. Check start, seek forward/backward, pause/resume, audio selection, subtitles and reconnect.
  5. For HDR or surround, check the display/receiver’s actual input mode rather than relying on a library badge.
  6. Report the result and conditions through the tester page.
