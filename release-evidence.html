Testing transparency

Evidence, not assumptions.

Beebo uses local checks, AI-assisted hand testing and human reports to find problems. They are useful together—but no one kind of testing proves every device, route or feature.

Every published result needs a build, a scope and an honest limit. A human tester is still needed on every release.

How to read this page

Four kinds of evidence. No shortcuts.

We separate what a check actually established from what is still unknown. A completed step is not automatically a passed feature, and a local result is not the same as a real-device result.

✓

Real-device confirmed

A named build was tried on a stated device, connection and feature path. It confirms that specific situation—not every setup.

⌁

Built or locally checked

Code-level and local checks help catch regressions. A person still needs to verify the experience in the packaged app.

?

Verification pending

There is not enough reviewed evidence to call this a pass or a failure yet. It stays visible instead of becoming an optimistic claim.

×

Needs more people or hardware

Some paths require another person, another device, a receiver, a tuner or payment access. One session cannot validate them alone.

Every feature: how far along, and what gets it to 100%.

How the percentage works. Every feature is scored against the same five checks, worth 20% each: Built (the whole feature exists), Automated tests pass, Real device (a person or helper tried it on a real phone or PC), Real-world check (a realistic situation, such as a real car, a second phone, away from home) and Ready to call Available (no known blocking gap). A tick means that check passed on the date shown; a dash means it has not. The last column lists exactly what is missing. 100% means every one of the five checks passed. It does not mean the feature can never fail. A percentage only moves when one of the five checks really changes. The automated test runs on the newest code prove the first two checks only; they say nothing about real devices. The status label is the one we use publicly: Available, Beta, In development or Planned.

What does “mostly proven” mean?

Every feature is checked five ways, worth 20% each: Built (it exists in the code), Automated tests (computer tests pass), Real device (it ran on a real phone, PC or TV), Real-world check (someone used it for real, not only a test) and Ready to call Available (we are comfortable calling it Available).

  • Green, 80–100%, “mostly proven”: 4 or 5 of the 5 checks passed. Almost everything has been shown to work; the open check is listed in the last column.
  • Yellow, 40–60%, “partly proven”: 2 or 3 checks passed.
  • Red, 0–20%, “early or not started”: 0 or 1 check passed.

A bar is not a promise that a feature is finished or free of bugs. It only counts how many of our own checks have passed, and a check only counts when we have real evidence for it.

Known limits of a solo pass

Not something one session can prove

  • Campsite guest joins and shared play need another participating device.
  • Casting needs a compatible receiver and a real network route.
  • Live TV needs the relevant tuner and broadcast setup.
  • Paid-service flows need authorised payment test access.
